# UI Quality Gate

这是一套可复用的 UI 工程质量范式，不是 CopyPaste 的单点问题补丁。任何面向用户的界面改动都可以套用：桌面 App、Web App、设置页、仪表盘、插件、弹窗、发布截图、视觉重构等。

UI 任务完成的标准不是“功能能跑”，而是：功能正确、信息结构清楚、布局秩序稳定、状态覆盖完整、容器变化可解释，并且在真实运行环境中完成视觉验证。

## 通用范式

### 1. 先定义产品界面问题域

动手实现前，必须先回答：

- 用户目标：用户在这个界面上要完成什么。
- 界面类型：设置页、生产力工具、仪表盘、编辑器、弹窗、插件、内容页、营销页或游戏界面。
- 平台惯例：macOS、Windows、Web、移动端、浏览器插件、IDE 插件等。
- 主要流程：用户最常走的操作路径是什么。
- 产品语言：界面语言、术语、语气、是否需要本地化。
- 约束条件：最小尺寸、是否可调整大小、主题模式、权限状态、数据量、可访问性和发布目标。

如果这些问题没有被明确，后面的实现就是在猜。

### 2. 先做信息架构，再做视觉样式

界面需要先有清晰的阅读顺序和内容层级。

- 明确一级、二级、三级信息。
- 相关控件放在一起，不相关分组用间距、标题或分隔线隔开。
- 标签必须靠近它说明的控件。
- 导航、标题、标签、控件、操作按钮要有稳定的视觉轴，不能各自漂移。
- 产品界面不能无意混用语言。
- 空状态、错误态、禁用态、加载态、权限缺失态属于信息架构的一部分，不是最后才补的文案。

### 3. 定义布局轴与空间归属

每一块可见区域都必须有用途。屏幕上的空间只能属于以下几类：

- 内容：数据、控件、预览、列表、编辑器、图表。
- 导航：tab、侧边栏、工具栏、筛选器。
- 分组：section 间距、分隔线、卡片内边距、行距。
- 呼吸感：用于提升可读性的有意留白。
- 系统 affordance：滚动条、resize 区域、窗口 chrome。
- 空状态：内容不存在时的明确说明或操作入口。

没有归属的大片空白就是 UI 缺陷。发现大面积空白时，只能选择以下处理之一：让有效内容消费空间、限制容器尺寸、引入滚动、重排布局，或者用明确空状态解释它。

编码前必须定义：

- 横向视觉轴：导航从哪里开始，内容从哪里开始，标签和控件如何对齐。
- 纵向节奏：标题间距、分组间距、行距、列表或卡片从哪里开始。
- 信息密度：紧凑、常规还是宽松，必须服务用户流程。
- 固定区和弹性区：哪些区域保持稳定尺寸，哪些区域吸收额外空间。

### 4. 对每个方向单独定义 resize 策略

只要界面支持调整大小，就必须分别定义宽度和高度的处理方式。

每个方向只能选择清楚的策略：

- 内容扩展：列表、网格、编辑器、预览或画布消费额外空间。
- 内容重排：列数变化、面板堆叠、控件换行。
- 内容滚动：内容超过视口时自然滚动。
- 容器封顶：当额外空间没有意义时，限制窗口或面板继续变大。
- 固定内容：固定尺寸控件保持稳定，由相邻弹性区域吸收空间。

不能用全局窗口尺寸锁去掩盖单个方向的问题。宽度问题和高度问题必须分开处理，并验证最小、默认、手动拉伸和实际最大尺寸。

### 5. 使用语义化视觉 token

颜色、字号、边框、间距、选中态不能靠随手参数。

- 定义 surface、elevated surface、border、primary text、secondary text、accent、selected、hover/focus、disabled、danger 等语义。
- 浅色和深色模式分别检查。
- 核心内容区域不要随意使用半透明灰色；除非这是被明确设计并验证过的交互。
- 原生 layer 背景色需要在外观切换时刷新。
- 字号要匹配容器和任务：重要设置不能小到像注释，密集工具也不能使用英雄区大字。
- 当前选中、当前筛选、当前位置必须一眼可识别。

### 6. 验证状态矩阵

每次 UI 改动都要有状态矩阵，范围可以随任务大小缩放，但不能为零。

- 主题：浅色、深色。
- 选择状态：普通、选中、hover/focus、禁用。
- 内容量：空数据、少量数据、大量数据。
- 文案：短文本、长文本、本地化文本。
- 权限：已授权、拒绝、未请求。
- 尺寸：最小、默认、用户手动调整、实际最大。
- 数据类型：常见类型和边界类型。
- 失败状态：加载、错误、服务不可用、输入无效。

### 7. 做真实视觉验收

构建通过和功能测试通过只是必要条件，不是 UI 验收。

必须尽量做到：

- 运行真实 App、网页或插件。
- 使用真实截图或真实界面检查，而不是只看 mockup。
- 检查对齐、分组、密度、对比度、选中态、resize、主题模式。
- 把真实结果和设计意图对照，而不是只确认“不崩溃”。
- 如果权限或环境导致无法截图，必须在交付说明里明确写出这个验证缺口。

生成示意图、草图、占位截图只能用于构思，不能作为实现正确的证据。

### 8. 提交前复审

提交 UI 改动前，必须能回答：

- 这个改动改善了哪个用户流程。
- 本次定义了哪些布局轴。
- 额外宽度和额外高度分别由谁消费。
- 最小、默认、手动调整尺寸下会发生什么。
- 浅色和深色模式是否都可读。
- 当前态、选中态、禁用态是否清楚。
- 产品语言是否一致。
- 有没有无意义空白、拥挤块、漂浮控件、错位控件。
- 哪些内容已经在真实界面中验证，哪些还没有验证。

如果回答含糊，说明实现还没准备好交付。

## 常见失败模式

- 把“功能可用”误当成“UI 完成”。
- 没有定义布局轴、密度和 resize 策略就开始写代码。
- 少量控件漂在大面板中间，没有稳定左对齐阅读路径。
- resize 后暴露大面积无归属空白。
- 用全局窗口尺寸限制掩盖单方向布局问题。
- 产品界面无意混用语言。
- tab、筛选器、导航项缺少明显选中态。
- 临时颜色在浅色或深色模式下变脏、变灰、对比不足。
- 标签和控件没有共享对齐系统，逐行漂移。
- 用生成图或 mockup 冒充真实实现截图。
- 构建通过后没有进行最终视觉检查。

## 参考基准

- Apple Human Interface Guidelines: Color
  - https://developer.apple.com/design/human-interface-guidelines/color
  - 使用可适配不同背景、外观模式和可访问性设置的系统或语义颜色。
- Apple Human Interface Guidelines: Dark Mode
  - https://developer.apple.com/design/human-interface-guidelines/dark-mode
  - 深色模式需要单独验证背景、层级、文本和控件状态。
- Apple Human Interface Guidelines: Layout
  - https://developer.apple.com/design/human-interface-guidelines/layout
  - 布局需要在不同尺寸下保持内容关系清晰。
- W3C WCAG Contrast Minimum
  - https://www.w3.org/WAI/WCAG21/Understanding/contrast-minimum.html
  - 普通文本对比度目标至少 4.5:1，大号文本至少 3:1。
- Nielsen Norman Group: Group Form Elements Effectively Using White Space
  - https://www.nngroup.com/articles/form-design-white-space/
  - 空白应该帮助建立关系，而不是成为布局剩余物。
- Nielsen Norman Group: Why Does a Design Look Good?
  - https://www.nngroup.com/articles/why-does-design-look-good/
  - 一致的对齐、排版和间距能显著提升可读性和整体感。

## CopyPaste 案例附录

以下内容只是这套范式在 CopyPaste v0.2 中的落地案例，不是通用规则本身。

### 经验教训

- 现代设置页曾经只完成了功能切换，没有完成产品级视觉验收。
- 中文产品界面中出现英文导航，违反产品语言一致性。
- 选中态不明显，用户无法立即判断当前位置。
- 设置窗口尺寸相对内容过大，形成低密度空面板。
- 设置表单混用了多套对齐方式，导致控件像漂浮在页面中。
- 浅色模式使用半透明灰色 surface，导致窗口发灰、发脏。
- 经典主面板 resize 后出现大量竖向空白，因为额外高度没有归属。
- 曾经用窗口级尺寸限制处理高度问题，风险是误伤宽度调整体验。
- 构建通过被过度等同于完成，真实截图复审介入太晚。

### 项目专项约束

- 现代设置导航使用中文：通用、快捷键、外观、忽略应用。
- 现代设置导航使用整行左对齐，并提供清楚选中态。
- 现代设置内容标题、说明和控件组保持稳定左侧阅读轴。
- 少量复选项使用分组标题加左对齐控件，不用标签列把控件推到中间。
- 设置窗口使用明确浅/深色 surface；主面板透明度不影响设置窗口。
- 经典主面板保持横向可调整。
- 经典横向卡片列表顶部对齐；额外高度不能让主要内容沉底。
- 经典主面板的高度策略和宽度策略必须分开处理。

## Definition Of Done

UI 任务只有同时满足以下条件才算完成：

- 请求的功能行为正确。
- 布局有明确的轴线、分组、密度和空间归属。
- 宽度和高度行为已按相关尺寸验证。
- 如果产品支持浅色/深色，两个主题都可读。
- 主要状态有清楚视觉反馈。
- 产品语言一致。
- 已进行真实视觉验收，或者明确披露未验证项。
- 提交前已按本规约复审。
